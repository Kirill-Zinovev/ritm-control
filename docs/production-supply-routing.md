# Общая поставка: рулонная печать и бокс

Опубликовано 20 октября 2026: основной агент RITM на порту 4318 и существующий Web App Assembly (версия 37, прежний URL). Проверочные сценарии не создают рабочие поставки и не записывают данные в Google.

## Поведение

В форме создания/добавления пользователь вводит общий состав и сначала проверяет распределение. Станок читается из актуальной «БАЗА FBO»: WB — «Вид станка по умолчанию», OZON — «станок». При ошибке lookup OZON допускается только точный поиск базового артикула в WB, откуда исходная формула и получает станок. «Кто печатает» не используется. Позиции с неизвестными, ошибочными или конфликтующими станками пропускаются; распознанные позиции можно добавить после явного подтверждения показанных количеств. Если не распознано ни одной позиции, запись недоступна и пустая поставка не создаётся. Превью связано с точным составом, названием, операцией и выбранным источником, живёт десять минут и проверяется повторно перед записью.

- Рулонная печать: 2-GO, УФ, УФ бел., УФ. бел, УФ двусторонний.
- Бокс: УФ планшет, DTF, XEROX.

Пропущенные артикулы, количества и причины сохраняются в журнале операции и отдельно видны в интерфейсе. Их можно скачать и открыть кнопкой «Дозагрузить пропущенные»: форма привязана к исходной общей поставке, заново читает станки и требует нового подтверждения. После подтверждённого добавления артикула в ту же поставку он исчезает из незавершённого списка; исходный аудит пропуска сохраняется. Изменение каталога между превью и записью требует нового превью. Неопределённые позиции не удаляются из базы и не попадают в производственные задания или Assembly до добавления.

Новый лист создаётся только для отдела с распознанными товарами. У подразделений одной поставки одинаковое название и общий постоянный идентификатор. Перед первым изменением проверяются обе таблицы, права и шаблоны. Дозагрузка проверяет повторы артикулов во всех уже связанных отделах.

Одна Google-операция атомарна только в пределах одного документа. Поэтому состояния каждого отдела сохраняются отдельно в существующем локальном хранилище (`productionSupplyOperations`). Потеря ответа переводит отдел в состояние сверки. Кнопка продолжения сначала проверяет уже отправленный точный план и никогда повторно не отправляет неподтверждённую запись. Подтверждённые отделы пропускаются; оставшиеся действия требуют явного продолжения владельцем. Новая операция блокируется до завершения предыдущей.

В developer metadata каждого производственного листа записан `RITM_SUPPLY`: общий ID, ревизия операции, фиксированные документы/ID листов и `ready`. Переход в `ready` происходит после проверки состава всех отделов. Assembly принимает состав, только когда все перечисленные источники доступны и имеют одинаковые подтверждённые метаданные. При частичной загрузке сохраняются предыдущие полные данные с отметкой недоступного источника. WorkLog не изменяется синхронизацией.

Старые позиции рулонной печати при подключении второго отдела сохраняют прежние ID. Позиции бокса имеют отдельную область идентификаторов внутри общей поставки. Работа сотрудников и упаковка сопоставляются по этим ID; совпадение артикула или имени листа не служит связью.

## Особенности бокса

Используется существующий шаблон «OZON МОСКВА 10_10» (gid 122063726) в документе «OZON БОКС». Исходный шаблон не меняется. Новая копия получает служебный UID в AC; формулы сохраняются, чужие ручные факты очищаются. R/S инициализируются как FALSE; монитор читает их как готовность печати/резки. Поле X не заполняется количеством, поскольку в боксе оно означает лишние экземпляры.

В проверенном шаблоне бокса H/I — ручные размеры печати. Копировать их от чужого артикула нельзя. В новых строках они остаются незаполненными, если нет исходной формулы; интерфейс показывает неизвестную площадь. Их заполнение остаётся отдельной производственной операцией. В рулонном шаблоне также встречается ручная ширина H; её нельзя переносить от другого артикула. Если размеры или расчёт не подтверждены, площадь отображается как неизвестная и для рулонной печати.

Текущая доработка охватывает создание и дозагрузку. Изменение/удаление позиции бокса выполняется в исходном листе. Отдельное удаление целого связанного задания через старый обработчик рулонной печати заблокировано: оно нарушило бы общую поставку. Старые несвязанные поставки сохраняют прежнее управление. Исторические листы бокса автоматически к одноимённым листам не присоединяются.

## Рабочее включение

По разрешению владельца обновлены основной агент RITM, клиентская сборка и существующий Apps Script deployment с сохранением URL. Отдельный writer агента имеет доступ к обеим таблицам; оба шаблона найдены, новые OAuth scopes не добавлялись. Настройки, ключи и рабочие листы не перезаписывались. SQLite сохранена через резервную копию и проверена после перезапуска: история, инциденты, эталоны формул и заявки сохранены. На рабочем API выполнено только превью по актуальной базе: LT0001.A5427 → УФ → рулонная печать, KS0006.A8368 → XEROX → бокс, несуществующий артикул → пропуск. Запись этой проверки не подтверждалась. После перезапуска требуется повторный вход владельца в AI Center.

После публикации выполнить владельцем согласованную рабочую проверку одной поставки с товарами обоих отделов и подтвердить её общий состав в Assembly. Локальные тесты не заменяют эту проверку.

## Проверки

Тесты охватывают маршрутизацию, суффиксы артикулов, пропуск неизвестных/конфликтующих станков с сохранением списка, полностью неопределённый состав, последующую дозагрузку и разрешение пропусков, повторную проверку каталога, предварительную проверку обоих получателей, потерю ответа Google, перезапуск, дозагрузку из бокса, защиту от повторов между отделами, ограничения owner API и объединение Assembly без изменений WorkLog. Проверяется отдельный шаблон бокса, его R/S и сохранность X. Браузерный сценарий изолирован перехватом API: превью без записи → смешанный состав добавляет только распознанные товары и сохраняет пропуски → изменение состава требует нового превью → однократное подтверждение → результаты по отделам.
