# Production readiness — подготовка, без запуска

Сервис не опубликован. Ветка feat/google-sheets-production-readiness продолжает архитектуру main 57a2286. Развёртывание с производственными данными требует отдельного подтверждения владельца.

## Рекомендуемая первая схема

Один VPS: постоянный Node 24+, Caddy, агент, SQLite WAL на постоянном локальном диске. Один агент на базу, аренда и heartbeat сохраняются. Docker restart=unless-stopped, init и SIGTERM обеспечивают перезапуск/завершение.

Публичный RITM остаётся на GPT Sites. Приватный AI Center обслуживается самим агентом на отдельном HTTPS-домене. Владелец открывает этот кабинет отдельно, проходит текущую авторизацию; никакие токены не встраиваются в GPT Sites/frontend. Прямой доступ публичного сайта к Windows localhost отсутствует. Для будущего единого кабинета потребуется отдельный серверный BFF и полноценная пользовательская авторизация, без публичных приватных API.

Caddy и агент используют общую сетевую область контейнера: Node слушает только 127.0.0.1:4318, наружу может публиковаться только 80/443 Caddy. По умолчанию даже эти порты привязаны к loopback хоста. Внешнее открытие — только после подтверждения, настройки firewall и разрешённых IP/VPN владельца. Caddy отклоняет остальные IP. Прокси не пишет access log с запросами/куки. Ключ владельца проверяется приложением; HttpOnly, SameSite=Strict, Secure cookie. Ограничение запросов применяется до обработки API. Origin разрешён только явным HTTPS-настройкам.

## Подготовленные файлы

- deploy/production/Dockerfile: отдельная сборка существующего frontend, постоянный непривилегированный Node-процесс, healthcheck.
- deploy/production/compose.yaml: только явный profile production, restart, read-only root FS, постоянные volumes, отдельные secret mounts, ротация Docker logs.
- deploy/production/Caddyfile: HTTPS, IP allowlist, ограничение тела, прокси к loopback Node.
- agent/backup.js: online SQLite backup с quick_check, без простого копирования основного файла WAL-базы.
- agent/healthcheck.js: приватное чтение собственного статуса с heartbeat; ключ не печатается.
- .dockerignore: исключение локальных данных и учётных файлов из контекста.

Это конфигурация к проверке на выбранном сервере: Docker/Compose здесь отсутствуют, build контейнера, ACME, firewall и восстановление на Linux не проверены. Node и Caddy образы перед запуском должны пройти проверку актуальных security patches и фиксацию digest. Нельзя считать прошедший frontend build проверкой контейнера.

## Хранение и резервное копирование

SQLite подходит первой версии при одном процессе и небольшом количестве инцидентов: текущие минимальные снимки диагностируются за миллисекунды. Не использовать сетевой диск и несколько пишущих экземпляров. Постоянный agent-data volume содержит БД/историю и журналы, права доступа ограничены.

Пример online-backup после подтверждённого запуска:

    docker compose -f deploy/production/compose.yaml --profile production exec agent node agent/backup.js /var/lib/ritm/intelligence.sqlite /var/backups/ritm

План: ежедневная системная задача с этим вызовом, минимум 7 дневных и 4 недельных копии, зашифрованная внешняя копия вне VPS, мониторинг срока последнего backup и свободного диска. Локальный backup сам по себе не защищает от потери VPS. Текущий CLI не удаляет старые копии; ротацию, внешний backup и уведомления нужно настроить до запуска 24/7.

Восстановление: остановить агент; проверить quick_check копии; сохранить текущий volume отдельно; восстановить копию как intelligence.sqlite в чистом каталоге без прежних WAL/SHM; проверить владельца/права; запустить ровно один процесс; проверить историю и актуальность. Тест online-backup/чтения восстановленной копии прошёл локально.

PostgreSQL нужен при нескольких экземплярах, централизованной авторизации, большом журнале или требованиях управляемого резервирования. Сейчас переход создал бы дополнительный серверный компонент без доказанной потребности; интерфейс store следует сохранить и добавить PostgreSQL-реализацию при этих условиях.

## Секреты и идентификация Google

На VPS JSON-ключ и ключ владельца монтируются отдельными файлами из защищённого каталога вне checkout. Google-ключ сохраняет роль reader только разрешённых документов, клиент запрашивает spreadsheets.readonly и не имеет операций записи. Не класть секреты в .env сборки, Docker image, logs, SQLite или frontend.

JSON на обычном VPS — компромисс первой версии. Для Google Compute Engine/Cloud Run предпочтителен attached service account либо Workload Identity Federation на поддерживаемом хостинге. В этой ветке эти способы не реализованы; клиент всё ещё использует JSON, и отсутствие key-файла не замещается чужим OAuth-токеном. Перед переходом добавить официальный Google Auth-провайдер с короткими токенами и проверить scope/identity/доступ. IAM-роли владельца проекта для Sheets не нужны.

Telegram выключен в шаблоне; после предоставления bot token/chat_id добавить отдельный secret mount и RITM_TELEGRAM_TOKEN_FILE, RITM_TELEGRAM_OWNER_CHAT_ID. Проверить одну авторизованную тестовую отправку, неопределённый исход не повторять автоматически. Входящих команд/исправлений нет.

## Необходимые параметры VPS

RITM_VERSION — проверенный SHA, RITM_BASE_URL — текущий Sites URL, RITM_AGENT_DOMAIN — отдельный домен, RITM_OWNER_IPS — разрешённые адреса/VPN, RITM_OWNER_TOKEN_PATH и RITM_GOOGLE_KEY_PATH — абсолютные приватные файлы вне Git. RITM_BIND_IP по умолчанию 127.0.0.1; нельзя открывать 0.0.0.0 до подтверждения и firewall.

Перед запуском: docker compose config; build; тесты образа на синтетическом источнике; TLS/allowlist/401/403/429; backup/restore; затем явно согласованный переход к reader-документам. Не запускайте docker compose up из CI автоматически. Обновление: проверенная версия → backup → остановка одного процесса → запуск проверенного образа → smoke-check. Откат: прежний image tag и совместимая резервная копия, не восстановление в работающую БД. Не применять docker compose down -v.

Healthcheck сообщает о heartbeat и доступности локального API. Сам по себе он не является внешним мониторингом: Docker restart policy перезапускает остановившийся процесс, но не просто unhealthy-контейнер. До 24/7 настроить внешний watchdog/uptime probe с ограниченным доступом, мониторинг lastCheck, зависимостей Google/Telegram, диска и backup; сценарий зависшего процесса отдельно проверить.
