# Утверждение диагностики и точечные исключения

Развивает существующий локальный агент и AI Center. Производственные документы доступны только для чтения. Утверждение диагностики НЕ разрешает запись, исправление формул, изменение KPI или прав сотрудников. Тест G247 остаётся отдельным незавершённым этапом.

## Четыре предложения правил

| ID            | Область                            | Эталон / сверка                                              | Условия                                                                                                   |
| ------------- | ---------------------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| fbo-sum       | «Все коэффициенты», E2:E10         | `=SUM(B{row}:D{row})`                                        | Текстовое имя с буквами в A; пустые/числовые специальные строки исключены                                 |
| supply-area   | «OZON НОВЫЙ ГОД», J4:J2000         | `=F{row}*H{row}*I{row}*O{row}`                               | Заполнен E, задан ненулевой O; это план, а не фактический KPI                                             |
| catalog-sum   | Каталог первого магазина, K2:K3000 | `=SUM(G{row}:J{row})`                                        | Заполнен текстовый артикул A; пустые направления допустимы, текстовые количества проверяются отдельно     |
| daily-journal | Сводка A5:D3000 ↔ журнал A2:O3000  | Сумма L по B/C/D: производственная дата, сотрудник, операция | Полный успешный снимок зарегистрированных областей; частичные выпуски складываются, печать/резка отдельно |

SUM(B:D) и SUM(G:J) получены из исходных формул; сокращения SUM(B)/SUM(G) не подменяют их. Для площадей не используются соседние ячейки как эталон. В журнале не требуются формулы в значениях фактического выпуска.

QUERY суммирует строки журнала без дедупликации. Эта сверка проверяет сводку, но не заменяет Worker: `worker/printing.js` продолжает исключать невалидные/дублирующиеся записи и учитывать только печать. ISO-время с явным часовым поясом группируется в Europe/Moscow; локальные даты и числовые даты Sheets сохраняют производственный день.

## Решение владельца

AI Center → Table Doctor → «Рассмотреть правило» показывает диапазон, условия, исключения, количество строк/групп, наблюдений и совпадений, влияния и версию. Владелец отдельно отмечает подтверждение и нажимает «Подтвердить диагностику». По умолчанию все четыре предложения pending.

POST правил принимает только ID из фиксированного списка, точную версию контракта и acknowledged=true. Требуется действующий HttpOnly/SameSite owner-cookie и точный разрешённый Origin. Bearer не разрешает принятие решения. Решения запрещены во время неполной проверки; утверждение требует свежего успешного чтения. Отзыв разрешён и при недоступном источнике. Решения идемпотентны и сохраняются в SQLite с историей владельца.

При изменении семантики/диапазона/исключений разработчик обязан повысить revision контракта; сохранённое утверждение другой версии не применяется. Следующий успешный цикл применяет правило. Старый инцидент сохраняет ID, если уже обнаружен прежним детектором: утверждение не создаёт его дубль.

## Классификация и исключения

В интерфейсе отдельно видны совпадения с эталоном, ожидаемое поведение, подозрения, нарушения утверждённой формулы и расхождения процесса. Совпадение формулы не доказывает корректность её входных данных. Отображаемый #N/A не признаётся поломкой без контекста строки/столбца.

«Допустимое исключение» требует причины 5–1000 символов и срока не более 90 дней. Область — ровно одно наблюдение: документ, gid, ячейка, правило, тип отклонения, версия правила и контрольная сумма доказательств. Изменение входов/формулы/значения отменяет применимость; срок ограничен, исключение можно отозвать. Другое отклонение в той же ячейке не скрывается. Исключение и отзыв правил приостанавливают соответствующую диагностику без ложного статуса «Исправлено». При возвращении проверки инцидент возобновляется с новой генерацией уведомления.

## Расследования

Карточка содержит факт, причину внимания, прочитанные формулы/значения с адресами и ссылками, предполагаемый механизм, ограничения, влияние и рекомендацию. Причина редактирования и бизнес-назначение повторов не угадываются.

- Дневной XLOOKUP может маскировать отсутствующего в сводке сотрудника нулём; это не доказательство отсутствия работы.
- P971/P1515 первого магазина объясняются реальной цепочкой P → S → Q с допуском ≤5. Это наблюдаемое условие источника, а не автоматически утверждённая новая норма.
- Повторы каталога сверяются с точным адресом OFFSET/N. Совпадение артикула само по себе не означает неоднозначную рабочую связь. Назначение повторных партий/вариантов подтверждает владелец.
- Остаток печати `IF(Q="Готов";0;O)` не реагирует на счётчик «N из M». Разность плана и доступного журнала — аналитический кандидат, не предложенная формула для записи: историческое покрытие журнала не утверждено.

Чтения разных частей/листов Google не атомарны. Изменения в ходе цикла могут потребовать повторного сравнения. KPI и структура производственных документов не изменяются.

## Производительность и сохранность

Проверяются все зарегистрированные области десяти листов каждый цикл, без кэша, пропуска строк или проверки только выбранных примеров. Новый документ рулонной печати добавлен только для чтения; его формулы плановой площади остаются неподтверждёнными. Рабочий лист первого магазина читается по 250 строк, каталог — по 500. Запросы последовательны с интервалом ≥2 секунды; цикл планируется каждые 600 секунд независимо от браузера.

Ответы запрашиваются с `prettyPrint=false`; формулы, userEnteredValue/effectiveValue и сообщения об ошибках сохраняются. Дублирующее formattedValue не запрашивается. Телеметрия показывает GET/OAuth, повторы, размеры JSON после распаковки, максимальный ответ, длительность чтения/диагностики и HTTP-коды. Замеры одного живого цикла не являются гарантией постоянного ускорения.

SQLite остаётся в защищённом долговечном каталоге, перед обновлением создаётся online-backup с quick_check. Добавлены таблицы diagnostic_decisions и diagnostic_exceptions; история и исключённые из мониторинга инциденты не удаляются. Автозапуск/lease/порт 4318 сохраняются. Тестовый агент 4319 работает отдельно, запись в production заблокирована.

## Проверки

`npm run typecheck`, `npm run test:intelligence`, `npm run test:sites`, `npm run test:domain`, `npm run build`.

Новые тесты покрывают точные эталоны, исключение специальных строк, текстовые количества, реальный допуск статуса, OFFSET, сохранение всех групп повторов, частичные выпуски/резку/московские даты, обязательное подтверждение, устаревший снимок/версию, дедупликацию, закрытие после исправленного тестового снимка, локальные исключения/отзыв/истечение/изменение входов, сохранность после перезапуска и запрет неавторизованных действий. Производственные Sheets в тестах не изменяются.

## Порядок рассмотрения

Сначала можно рассмотреть проверку плановой площади и сверку дневной сводки с журналом: при отсутствии отклонений владелец всё равно подтверждает условия, ручные значения и полноту области. Затем — сумму FBO с исключением специальных строк. Для каталога нужно предварительно разобраться с нечисловыми входами и допустимыми ручными корректировками. Это рекомендация порядка рассмотрения, а не автоматическое утверждение. Подсказка в карточке учитывает текущие отклонения и недоступность/устаревание источника.
