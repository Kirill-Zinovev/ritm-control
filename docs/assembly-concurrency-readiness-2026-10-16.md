# RITM Assembly: готовность к параллельной работе

Дата: 2026-10-16. Изменения подготовлены локально; рабочий Apps Script не обновлялся, нагрузка в Google не запускалась.

## Что улучшено локально

- Поставка загружается одним вызовом `getInitialData`; список и раскрытие позиций остаются клиентскими. Раскрытие одной позиции обновляет только её карточку.
- Фото больше не передаются в начальном ответе. Видимые изображения запрашиваются лениво небольшими пакетами до 20 ключей.
- Справочник сотрудников и нормы кэшируются на 5 минут только для отображения. `saveWork` перечитывает сотрудника и норму из таблиц перед записью.
- Обновление клиентов опрашивает только версию в Script Properties с фазовым случайным интервалом 45–60 секунд. Полные данные перечитываются только при новой версии или ручном обновлении; введённые формы не сбрасываются.
- Синхронизация печатных листов резервирует короткую блокировку, освобождает её до чтения/записи поставок и снова берёт только для публикации результата. Дубликат запуска блокируется lease на время, превышающее предельные 6 минут выполнения Apps Script.
- `saveWork` проверяет поставку, позицию, сотрудника и норму до блокировки. Внутри блокировки повторно проверяет `idempotencyKey`, одной операцией дописывает строку WorkLog и увеличивает версию данных. Вместо ожидания до 20 секунд запрос сдаётся с понятной ошибкой, если короткую блокировку нельзя получить за 5 секунд.
- После неопределённого ответа UI сначала запрашивает запись по ключу операции; сетевой повтор использует тот же ключ. Успех показывается только по подтверждённому ответу или найденной строке WorkLog.

Все клиенты увидели новую версию прогресса. Для каждого размера группы создан один синтетический короб, его вместимость достигнута ровно, переливов не было; повтор одного ключа не добавил строку. Метрики показывают только поведение этой модели.

Коробовые API реализованы в локальном Apps Script источнике: список фильтруется по поставке, создание и размещение — отдельные append-only операции с idempotencyKey и повторной проверкой на сервере. Новые Cartons хранят стабильный shipmentId в добавленной крайней колонке; старые поля остаются на месте, WorkLog не меняется. Контрактные тесты и синтетическая нагрузка проверяют изоляцию поставок, повторы, отказы вместимости и тайм-ауты. Производственная таблица и реальная конкуренция Apps Script не проверялись; модель не доказывает транзакционную изоляцию с внешними редакторами.

## Ограничения, которые остаются

1. По выбранному сценарию сотрудник указывает своё имя при записи; отдельный PIN не добавлен. Интерфейс сохраняет этот простой выбор, а сервер проверяет, что имя есть в активном справочнике. Сам выбор имени не подтверждает личность: при общем публичном доступе запрос технически можно отправить с чужим `employeeId`. Значит, это учёт по самоидентификации, а не защищённая персональная авторизация.
2. Google указывает лимит 30 одновременных выполнений Apps Script на одного пользователя и 1 000 на проект. Для Web App, который выполняется от имени владельца, эти 30 выполняемых запросов делятся между всеми сотрудниками и триггером. Число 30 — верхний предел, а не гарантия пропускной способности; лимиты Google меняются. См. [официальные лимиты Apps Script](https://developers.google.com/apps-script/guides/services/quotas) и [модель авторизации Web App](https://developers.google.com/apps-script/guides/services/authorization).
3. `LockService` делает конкурентные добавления в WorkLog последовательными. Повторная проверка ключа под блокировкой защищает от одинаковых повторов внутри этого проекта, но Google Sheets не предоставляет транзакцию сразу между WorkLog и Script Properties. Для высокой частоты записи остаётся узкое место.
4. Это не проверка настоящих одновременных пользователей. Нет измерений p50/p95 от сети до Google, фактического времени блокировки, лимитов конкретной учётной записи, ошибок API и обновления настоящих страниц.
5. Доступ к публичной странице и чтение данных не привязаны к подтверждённой личности сотрудника. Это предшествующее ограничение развёртывания, оно не закрывается локальным нагрузочным тестом.

## Что нужно до заявления о 20–30 сотрудниках

- Если требуется гарантировать, что сотрудник не может записать операцию под чужим именем, добавить отдельную серверную идентификацию. Для текущего выбранного сценария без PIN имена остаются самоуказанными и не являются доказательством личности.
- Провести отдельную разрешённую нагрузочную проверку на изолированном стенде, не на производственных таблицах, собирая фактическое ожидание блокировок, задержки Apps Script/Sheets, квоты и процент ошибок. Отдельное опубликованное тестовое/демо-приложение для текущей задачи не создаётся.
- После подтверждения схемы основного хранилища проверить коробовые операции по его snapshot-копии или тестовым фикстурам, сохраняя append-only историю и ограничения вместимости.
- Если тест показывает очереди или лимиты, вынести операции на существующий backend RITM и транзакционную базу: уникальный индекс idempotency key, транзакция для остатков/коробов и журнал операций; Google Sheets оставить синхронизируемым представлением через очередь/outbox.

До закрытия пунктов 1–3 этот прототип не является подтверждением безопасной производственной готовности на 30 пользователей.
