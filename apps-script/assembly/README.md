# Связь поставок RITM → печать → сборщики

## Обновление каталогов · опубликовано 22.10.2026, версия 63

Название поставки определяет источник: OZON/ОЗОН читает только OZON, WB/ВБ — только WB. Это правило действует для товарных сведений, магазинов, этикеток и вместимости коробов; кэши норм разделены по маркетплейсу. Кнопка «Обновить» принудительно перечитывает справочники, включая OperationNorms и сотрудников, даже при неизменном составе поставки. Старая подтверждённая вместимость удаляется из кэша перед принудительной проверкой, поэтому конфликтующее или отсутствующее новое значение не возвращается к прежнему через краткую карточку короба. Конфликты показываются как требующие проверки, с причиной в подсказке. WorkLog, исторические коэффициенты и содержимое коробов сохраняются.

Опубликовано в прежнее развёртывание и URL; режим выполнения, доступы и manifest не изменялись. Перед публикацией сохранена копия удалённых трёх файлов вне репозитория. Проверки: 133 теста Assembly и конкурентный сценарий на 5/10/20/30 клиентов. Источники каталога и печати не редактировались.

Основной RITM Assembly Web App принадлежит владельцу. Script ID, URL и spreadsheet IDs хранятся в закрытой локальной конфигурации и не публикуются в этом репозитории. Обновлять можно только подтверждённое существующее развёртывание, сохраняя URL.

## Поток данных

1. Владелец создаёт поставку штатным подтверждением RITM. Существующий `RollSupplyManagementService` создаёт и проверяет вкладку в `OZON РУЛОННАЯ ПЕЧАТЬ`.
2. `syncRitmSupplies` читает только видимые вкладки с заголовками E4 = «Артикул», O4 = «Кол-во». Служебные и скрытые вкладки исключены.
3. В существующем хранилище приложения сборщиков создаётся одноимённая вкладка. E и O источника дают артикул и план; AC даёт стабильный UID. Исходная таблица печатников не изменяется.
4. Товарные сведения читаются только из видимых «OZON» и «WB» настроенной базы каталога. Для «OZON» используется алиас из столбца B без заголовка, для «WB» — поле «Артикул (oz)». Не найденные товары остаются в поставке с артикулом и планом.
5. Приложение выбирает поставку по серверному ID и читает её вкладку. Работа записывается существующим `saveWork` в append-only WorkLog с точными shipmentId/directionId/positionId. Одинаковые артикулы разных поставок не смешиваются.

## Частота и границы

Переход между поставками читает локальное зеркало сборщиков и не запускает повторный обход таблицы печатников. Уже открывавшаяся поставка показывается из кэша сразу, затем тихо обновляется с локального зеркала. Кнопка «Обновить» принудительно сверяет источник печатников. Автопроверка каждые 45–60 секунд читает только версию; поставка перечитывается при её изменении. `installRitmSupplySync` устанавливает один фоновый минутный триггер; повторный запуск установки не размножает триггеры. Google может задержать выполнение триггера, поэтому минута — целевой интервал, не гарантия доставки.

Для быстрых ответов приложение сначала читает только колонку ключей WorkLog/Photos и загружает полные данные только для выбранной поставки и её фото. Проверка повтора при записи также ищет ключ только в индексной колонке журнала, а не перечитывает все исторические строки. После подтверждённой записи экран обновляет только изменённую позицию из ответа операции; полный повторный запрос всей поставки не выполняется. При потерянном ответе приложение проверяет прежний ключ, получает сведения о сохранённой операции и обновляет только эту позицию.

Исправление задержек от 20.10.2026: подтверждённые задания участков синхронизируются перед обновлением старых вкладок; метаданные рулонных листов переиспользуются в пределах одного прохода. Нормы коробов читаются пакетно: одно обращение к кэшу и не более трёх диапазонов на каждый видимый лист каталога (заголовки, ключи, только колонки норм). Запись в короба по-прежнему перечитывает нормы без кэша. Быстрое обновление прогресса приносит также актуальный список поставок, поэтому новая поставка становится доступна до завершения полной загрузки справочников. Переключение отменяет применение устаревших ответов; неполный предварительный состав не попадает в кэш готовых рабочих снимков. Минутный триггер и его возможная задержка Google сохраняются.

## Локальный интерфейс сборщиков · 16.10.2026

Список поставок слева, компактные товарные строки, таблица сотрудников без встроенных форм. «Записать работу» открывает одно окно с уже выбранным артикулом, активным сотрудником, доступной операцией и количеством. Выбор имени запоминается на устройстве и не служит авторизацией. «Короба» открывает правую панель с привязанными к текущей поставке коробами. Создание короба и размещение товара вызывают отдельные серверные операции с idempotencyKey; сервер проверяет остаток, вместимость и статус перед append-only записью в Cartons/CartonContents. Новые короба сохраняют стабильный `shipmentId` в колонке, добавленной в конец `Cartons`: существующие строки и поля не сдвигаются, а legacy-записи без ID читаются по прежним полям. Полные события истории не выдумываются из агрегатов. На телефоне — карточки, на компьютере — таблица. Без запроса отображается не более 60 позиций с кнопкой продолжения; поиск работает по всему составу.

Факты команды строятся по событиям WorkLog и сопоставляются по стабильному `employeeId`; пустые подписи восстанавливаются из `Employees`, а события без ID остаются отдельными и не объединяются по похожему имени. В истории артикула показываются конкретные WorkLog-события. Для ошибочной записи приложение добавляет отмену в `WorkLogCorrections`; исходную строку WorkLog не удаляет и не переписывает, а отменённое событие исключает из прогресса и коэффициентов.

`node scripts/assembly-ui-preview.mjs` из корня проекта поднимает локальный просмотр на `http://127.0.0.1:4327`. Это ровно Index.html с тестовым RPC-адаптером и помеченными синтетическими данными. Адаптер не использует Google/учётные данные и не попадает в опубликованный Index.html. Параметры `?scenario=lost-response`, `?scenario=reject`, `?scenario=unknown`, `?scenario=offline` проверяют состояния сбоев. Публикация этой версии требует отдельного подтверждения владельца.

Обычный Apps Script onChange не подходит: изменения из Google Sheets API не запускают его. Используются проверка при чтении и time-driven trigger (https://developers.google.com/apps-script/guides/triggers/installable).

Локальная разработка не меняет Google Sheets, SQLite, эталоны или основной агент. Существующие листы Shipments/Items/WorkLog/OperationNorms/Photos/Cartons/CartonContents сохраняют строки, ID и порядок полей; при первом создании нового короба один технический заголовок `shipmentId` добавляется в конец `Cartons`. Никаких строк не вставляется в середину таблиц. Производственная совместимость должна быть подтверждена сравнением с правильным основным хранилищем до публикации.

Нет записей об операции — «—» с доступным пояснением, а не утверждение о нулевом выпуске. Норма коробов, вместимость и коэффициент не выводятся друг из друга. Отсутствующие нормы/короба остаются неизвестными. Упаковка и сборка не объявляются выполненными по печатным данным.

Листы сборщиков имеют явную метку источника A1 note. Чужой одноимённый лист не перезаписывается. Синхронизация идемпотентна; копия после прерванного создания принимается только с точной меткой. WorkLog не очищается. Если печатный лист удалён, отмеченная вкладка сборщиков переименовывается в архив, исключается из приложения, а журнал сохраняется; записи в удалённую поставку блокируются. Скрытый, но существующий источник остаётся различимым: его лист не архивируется автоматически и новые записи блокируются до возвращения видимости.

Если удалённый печатный лист создан заново под тем же названием, у него новый ID. Прежняя зарегистрированная производная вкладка сборщиков переименовывается в «название · архив ID», её строки и WorkLog сохраняются. Создаётся новая одноимённая рабочая вкладка с новой идентичностью; прежний прогресс не наследуется. Скрытый, но существующий источник и незарегистрированный лист не архивируются автоматически.

Перед запуском владелец задаёт в Script Properties значения `RITM_ASSEMBLY_DB_ID`, `RITM_LABEL_FBO_ID`, `RITM_LABEL_OZON_CODES_ID`, `RITM_ROLL_PRINTING_ID`, `RITM_BOX_PRINTING_ID`, `RITM_CATALOG_ID` и `RITM_PHOTOS_ID`. Код останавливается с понятной ошибкой, если обязательное свойство отсутствует или имеет неверный формат. Не сохраняйте эти значения в Git.

## Обновление существующего Apps Script
Цель — существующий основной Web App, подтверждённый владельцем. Перед публикацией проверьте ID проекта, таблицы и существующее развёртывание; обновляйте тот же deployment, не создавая тестовый.

Текущее web-развёртывание настроено на доступ «Все» и запуск от имени владельца, с подтверждения владельца 15.10.2026. Любой человек со ссылкой, включая без Google-аккаунта, может просматривать поставки и отправлять записи работы; журнал будет изменяться от имени владельца. Не размещайте ссылку публично шире нужной аудитории.

Для найденного тестового проекта созданы закрытые копии Apps Script исходников/манифеста и связанных таблиц; кодовый backup не переносит Script Properties, триггеры или deployments — Google хранит свойства отдельно для каждого script ID ([официальное описание Properties Service](https://developers.google.com/apps-script/guides/properties)). Перед работой с основным проектом отдельно экспортировать нужные настройки и записать ID существующего deployment; не копировать найденный тестовый проект как production target.

После подтверждения правильных ID сохранить резервную копию хранилища и текущих `Код.gs`/`Index.html`. Заменить содержимое «Код.gs» на `Code.gs` и «Index.html» на `Index.html`. Сохранить, выполнить `installRitmSupplySync` как владелец проекта, затем обновить существующее deployment новой версией, сохранив URL, режим выполнения и доступы. Если Google запрашивает новые разрешения, их должен проверить и принять владелец.

Не требуется перезапускать Windows-агент. Не создаётся публичный callback или новый механизм записи в таблицы печатников. Установка триггера дополнительно проверяет активный и эффективный аккаунт владельца.

## Проверки

`npm run test:assembly-app` — изолированные тесты синхронизации, каталога, изоляции поставок, переключения, дедупликации, сбоев сети, блокировки, восстановления после прерывания, пропусков и owner-only установки. `npm run typecheck`, `npm run build`, существующие тесты Intelligence/domain/Sites проверяют отсутствие регрессий RITM.

Синтетическое создание не является живым подтверждением: окончательный критерий — новая реальная поставка, созданная владельцем через RITM, одноимённые вкладки в обоих хранилищах и соответствующие артикулы в app.

Локальная UI-проверка 16.10.2026: 38 тестов Assembly, отдельный синтетический сценарий на 5/10/20/30 клиентов, 18 domain, 29 Sites/production parsers и 294 Intelligence; typecheck и production build проходят. Браузером проверены ширины 375/390 px, переключение поставки, поиск, раскрытие, модальное окно, синтетическая запись работы с обновлением только выбранного артикула, создание и размещение товара в короб. Локальный preview использует тестовые SVG-фото и синтетический RPC-адаптер, без Google API и производственных записей. Настоящий телефон, реальные фотографии и опубликованный Web App не проверялись.

Статический UI-аудитор выдал 11 предупреждений о кнопках Index.html: он распознаёт inline-обработчики, но не существующие привязки addEventListener. Отдельный исполняемый тест проверяет, что каждая статическая кнопка имеет обработчик либо нативную отправку формы; рабочие действия также проверены браузером. Общий аудит корня обнаружил ещё 8 замечаний в прежних React-экранах, которые не менялись в этой задаче. Статические отчёты сохранены вне репозитория; чистое прохождение этого аудитора не заявляется.
