# Assembly v2 behavior

Stock work can optionally include a second distinct operation with its own actual employee and positive integer quantity. Each operation freezes its own quantity, norm and coefficient. Finished stock uses only the packing operation's quantity. A single idempotent warehouse.receive command validates both entries, then commits both ledgers and signed RITM events atomically. Older clients that omit additionalWork.qty retain their original same-quantity behavior; new forms explicitly require a second quantity. Cancellation remains independent. Ready-stock receipt mode never includes extra work.

An owner-confirmed product image is a separate SKU-keyed override with actor/time and command audit. It takes precedence over imported catalog and signed source photos for current and future positions and declared catalog aliases. The original import files, work norms and stock are unchanged. Collectors cannot assign images.

Source photos are independent from production catalog matching. ProductPhoto prefers a verified RITM public image, then existing catalog/proxy alternatives; images load lazily with no credentials or referrer. The per-position source-photo cache is refreshed by signed feed sync even when the supply composition is unchanged; only actual image changes advance the view revision. Image changes cannot change quantities, source scope, historical work norms or carton contents. Missing source images remain explicit rather than guessed.

17 November correction: WorkDialog always offers manual cutting alongside any required machine cutting and packing. In the stock form, select work/ready-receipt, then operation and employee for work. Cutting records are separate from finished inventory; only packing adds finished goods. Each operation freezes its actual employee, norm and coefficient, reaches work history and RITM once, and cancels independently. Existing received stock earns no work.

Owner Warehouse uses NativeSelect filters for recognized city (shared directionCity aliases; unknown destinations stay exact), marketplace and shop. The city Excel action includes all matching closed unsent cartons across pages; the selected Excel action uses exact selected IDs. Both reread the authoritative full snapshot before download and reject carts whose departure/closed state changed. The workbook contains cartons, contents, SKU totals and timestamp/revision. Downloading this current-stock report never prepares or sends a departure; formal departure exports keep their existing persisted snapshot workflow.

Working navigation contains only source-active RITM supplies. Imported archives stay in the full journal and never reappear as working destinations. Direct journal links may open their original archived source outside working navigation. Archived source plans do not enter an active direction's summary.

14 November collector correction: navigation groups recognized marketplace/city/store using the legacy `cartonDirection_` aliases. Source supply IDs, positions, duplicate article rows, norms and per-source locks remain unchanged; `sourceSupplies` provides original ownership for forms. Unknown cities/stores stay source-specific. The source task disclosure lists every member. Only collector workspace requests opt into this read model; journals, RITM and exports retain source IDs and scope. Group reads detect concurrent revision changes rather than mixing totals.

Packing cancellation is one revision-guarded transaction: active work is attributed FIFO within the exact original position; its placed share is removed, including partial allocations. The original work and immutable allocation before/after audit remain. A changed closed carton reopens for verification. A prepared/sent departure or warehouse-stock share blocks the whole cancellation without partial effects. Cutting cancellation never changes packing or carton contents. Work cancellation, counters and its RITM cancellation event commit together; a repeated command cannot subtract twice.

14 November employee-access decision: no employee login or PIN. Use the owner's shared workplace link, then the existing employee selector. Access.tsx owns opening the link, feedback and the owner's copy-link control; server/access.ts authorizes each API and command. Owner and service permissions are separate. See docs/employee-cutover.md. WorkHistory displays saved norm/coefficient and filtered uncanceled totals with an explicit count of unknown coefficients. Source-data exceptions remain visible.

Separate new application; old code, data, deployment and processes must remain unchanged. Visual reference: DESIGN.md. Russian UI, ru-RU numbers, Europe/Moscow time.

14 November integration: collector snapshots contain only cartons in the selected marketplace/store/destination; manager screens load the full list before showing stock actions. Restored source records retain employee attribution, cancellations, original carton names and RITM sent statuses. A missing historical carton capacity is explicit and prevents further placement. Work saves commit locally with their RITM outbox event and return before network delivery. See docs/production-migration.md.

The user's 2026-11-13 correction supersedes the previous visual concept: reproduce the existing compact Assembly workspace. Supplies are on the left (latest explicit correction). Work uses a native modal; carton placement uses a right drawer, not a permanent side editor. Both reuse the shared Dialog, Field/NativeSelect and Button owners. Successful work closes its modal and returns focus to the article action. Placement keeps its drawer open and clears quantity only after ACK. Employee preference is session-only. Collector datasets use explicit “Показать ещё” in batches of 60, as the old interface; other screens keep their bounded pagination.

Completed tab: positive plan AND packing >= plan AND boxed >= packing. All packed surplus must be allocated before the product leaves “В работе”. Readiness is (packing + boxed)/(plan*2), with the original floor at <=100% and ceil above 100%; bar geometry is capped at 100%. Cutting does not reduce readiness. Unneeded cutting operations are not offered unless they have a positive plan or actual work. Catalog-matched positions show real photo/product/box types and enable the type filter. Unmatched positions retain explicit placeholders. Label assets, payroll norms and production tasks are not fabricated.

## Workflow and state

14 November correction: preserve last selected supply in browser preferences; records always live in D1, never browser storage. Without a valid preference the server opens the most recently worked supply. The «Выработка» journal queries all supplies with server pagination (20), supply/employee/article filters and direct links to the article with `filter=all`. The collector's selected-supply snapshot remains bounded at 100 recent work entries; this is not the journal's history limit.

Warehouse parity: «Короба → На склад» is a separate physical-stock ledger. Manual receipt selects a real versioned catalog card, exact marketplace/store, positive integer quantity and active employee; it creates no work or synthetic supply/position. Existing warehouse cartons/history are not automatically imported from the old database. The empty state states this explicitly. Dedicated warehouse tables are added without changing previous records.

Warehouse current carton is the latest open carton within exact market/store, independent of destination; labels use confirmed store + `скл` + next occupied number across v2 cartons and imported number reservations. Unlike direction-box drafts, the explicit warehouse «Новый короб» creates an empty current container, as in the original. Cartons never auto-split by SKU or capacity. Closing requires inline confirmation and an unchanged carton version; it never sends anything. Receipts retain pinned catalog/photo, origin, employee, comment and Moscow timestamp. Warehouse lists page five cartons, receipts load 30 per carton then explicit more; filtered empty/error/loading states retain controls.

`allocation.place` defaults to placing the whole entered quantity in the selected direction carton, including deliberate over-plan shipment. Like old Assembly, excess reveals «Куда направить излишек?» with «В выбранный короб» as the default. Only an explicit «На склад» choice splits the request into remaining shipment plan and warehouse excess. Capacity and confirmed packing remain mandatory; a full carton never silently redirects stock. The warehouse choice requires employee attribution and never repeats packing/KPI. One command key/revision covers both sides; validation failures roll back the entire operation. Closing/reopening the UI never rewrites work. No real test receipts are written to cloud.

The warehouse form explicitly distinguishes «Новая упаковка — учесть кэф» and «Приём готового остатка — без кэфа». New packing saves the actual warehouse receipt and a frozen work coefficient atomically, without inventing a supply or adding shipment progress. `av2_warehouse_work` owns this ledger; it appears in the shared employee history and is delivered once as a signed `warehouse-work` event to RITM. Unknown norms remain explicit, never zero or invented. Ordinary receipts and redistribution of already-recorded packing add no work. Canceling new warehouse packing in an open carton preserves both original records, voids only its receipt, and delivers a separate KPI cancellation; closed cartons require warehouse reconciliation and cannot be silently changed. Historical receipts receive no retroactive work.

Employee name is a business attribution, never authentication. The workplace link grants collector permissions; management and exports require the owner. Anonymous data requests fail closed. Collector navigation offers assembly and history; warehouse receipts remain in the carton drawer. No employee account or PIN is created. Every command passes server authorization.

Work operations: cut, assembly, packing, positive integer quantity, active employee. As in old Assembly, exceeding plan or packing before cutting is not blocked. Work can be canceled with a recorded reason only while resulting packed stock remains sufficient for existing allocations. Cancellation appends an audit record.

Allocation uses confirmed packing minus allocations across all cartons. It never increments production. Require a positive known units-per-carton norm and compatible marketplace/store/exact destination. Mixed fill is sum(qty/norm) <= 1. Save work + allocate is one transaction. Closed and reserved cartons cannot receive stock. Closing an empty carton is forbidden. Closed cartons remain unsent until a dispatch is explicitly marked sent.

The owner reconfirmed the old carton workflow and numbering on 13 November: “+ Новый короб” selects a local draft; the carton row and its first allocation commit together only after “Создать и добавить”. Abandoning the draft writes nothing. Numbering uses the confirmed store number, the original supply title's first three letters after the legacy normalization, then the next occupied numeric sequence, e.g. `1мос258`. Imported legacy number reservations include closed/cancelled boxes and prevent resetting an existing prefix to 1. Allocation creation uses the revision guard and a unique label index for simultaneous users. Existing saved carton labels are never renamed. Legacy and v2 counters remain independent after the one-time reference snapshot; employee cutover must include a fresh number-reference read before live use of both environments could overlap.

The real collector-name subset is read once from the existing Employees reference using the live old application's active/blue-building filter. Synthetic names are deactivated, retaining their work/history. Names are attribution only. Remember a valid selected name during the session and focus quantity on the next entry. An optional “После записи перейти к коробам” shortcut opens allocation after the confirmed packing ACK; it never infers or duplicates packing.

Locked supplies keep their RITM lock. Show “Закрыта в РИТМ” in navigation and a visible reason in the selected supply; never call this a missing department readiness check or silently unlock the old source. Missing packing/norm/store has explicit drawer guidance. Ordinary carton details do not expose raw RITM UUID/position IDs.

Dispatch draft reserves chosen closed cartons atomically. Dispatch cancel releases reservations, preserving audit and snapshots. Sending requires a review dialog and explicit action; downloading never sends. Export snapshots retain exact carton contents independently from subsequent state changes.

## Data and navigation

Cloudflare D1 with indexed relational tables, append-only work/corrections and transactional materialized position/team totals. Supabase new free project creation was refused because the account has two active free projects; no existing project was paused or modified. One initial selected-supply snapshot; one lightweight revision check every 30s while visible; reload only on changes and focus. No Google calls in the collector path. Forms preserve values on failure. Quantities clear only after server-confirmed save. Device storage contains only optional employee ID, selected supply, last compatible carton and view preferences, versioned; no stock records.

Supply import is authoritative only for the new environment. Preserve RITM external supply and position IDs. Versioned upsert must reject stale payloads and incompatible source changes for positions with history. Never collapse equal SKUs from different positions. RITM supplies also arrive through the separate authenticated read-only feed described in docs/RITM-CONNECTION.md. Legacy Assembly delivery remains unchanged. JSON import remains available as a standalone fallback.

Lists have explicit paging and query/filter state in URL. Selection survives page changes, resets on scope change and removes unavailable cartons after a refresh. Button duplicate submission is blocked; transport retry reuses a command key and exact payload, preventing double work. Stock mutations are pessimistic. Offline errors preserve drafts; no silent queuing. Visible retry and persistent error message.

## Product labels

Warehouse stock uses the same LabelDialog, original-label store and print path as supply positions. Resolve labels from an actual active catalog entry (before work/receipt) or a non-void warehouse receipt joined to its real market; never require a supply or substitute a product photograph/barcode. Single labels can download their immutable original through the authenticated same-origin image route. Printing/downloading cannot mutate work, stock or dispatches.

An erroneous warehouse receipt can be removed with a reason and exact carton-version guard. New warehouse packing removal cancels its own work/coefficient and emits the existing RITM cancellation atomically; cutting is independent. A ready receipt removal earns/cancels no work. A supply transfer removal releases that receipt's boxed quantity while preserving production work. Originals and command audit remain. Closed warehouse cartons require an explicit confirmed reopen before correction, then an explicit close afterwards; no silent status changes.

Expanded product rows retain the old «Этикетка» action, an original preview, copy presets 1/10/50/100, and a quantity of 1–999. «В печать» selects at most 150 exact positions across the current direction and pages; filtering does not silently clear selection, changing direction does. Removed positions are pruned. The combined dialog keeps missing/conflicting originals visible and prints only the explicitly available entries; a maximum of 1,000 total copies is allowed. One original image is placed on each print page with the printer's selected paper size, as in the old Assembly. No label is regenerated from a barcode or replaced by a product photo. The print window opens only on the user's print action; blocked popups, failed originals, and network errors preserve quantity/selection and allow retry. The application does not claim physical print completion or record work/carton changes from printing. Shared label responses and images require the collector or owner role; source import and file upload are owner-only. Work loading never reads the labels source or Google Sheets. Label imports stage immutable, hashed originals and complete source chunks before atomic activation; existing active labels remain available during upload.

## Excel

Accounting exports: Cartons, Contents and Summary; IDs and barcodes are strings. Marketplace exports use an uploaded user template and explicit mapping; no official compatibility claim without actual validated template. Template preview required before download. Excel generation loads only on demand and runs in the browser, outside the worker CPU budget.

## Catalog

The owner's “Управление → Справочник” uses the shared native controls, Dialog, Search, Pagination and feedback vocabulary. Server pagination is 30 cards, query/filter/page state is namespaced in URL, search debounces 300ms and cancels stale requests. The read-only card retains its source revision, marketplace/store, explicit aliases, all source rows and cell references. Excel error strings, missing essential data and duplicate conflicts are visible; no silent OZON-to-WB overwrite. See docs/CATALOG.md for exact source mappings, counts and the single confirmed 700 override.

Two-file preview parses in an on-demand browser Web Worker. Import stays in a busy modal, blocks duplicate submission and announces staged progress. Failed transfer retains its selected files/preview; retry skips accepted content-hashed chunks. Success closes the modal and returns to the filtered list with persistent success feedback. Unsaved selected files use the shared DraftGuard. Import activation is atomic and changes the common revision; old supply positions, work, allocation capacities, exports and sent contents remain unchanged. The ordinary collector snapshot has a bounded indexed catalog JOIN; photos use fixed geometry and lazy loading with an explicit failure placeholder. R2 photo caching is bounded, while gallery URLs and archived Excel originals remain private and durable. Full media mirroring and employee sharing are not implied.
