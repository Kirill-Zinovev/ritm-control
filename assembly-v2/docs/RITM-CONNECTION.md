# Separate RITM source channel

13 November lock correction: a live read through the old Assembly control channel confirmed Kazan shop 2 and Ekaterinburg shop 2 were already canonically unlocked. The feed now reuses RITM's own canonical lock resolver, without applying historical physical-sheet locks to a shared supply. No unlock is sent to RITM or Apps Script. A newer canonical lock checkpoint advances the feed revision even when the printing composition is unchanged.

Carton contents share `CartonProduct` in the compact list and details dialog, with a lazy photo, product name, source supply and quantity badge. Photo lookups use each position's pinned catalog import/entry; viewing a carton never invents a photo or changes its quantities, norm or saved export history.

The owner authorized supply transfer into this new app on 13 November 2026 and explicitly corrected the supply navigation to the **left**. The current sidebar uses the original Assembly layout; forms, stage bars, article rows and carton drawer remain familiar. Earlier references to right-side supplies describe the superseded request.

RITM exposes only a new, independently authenticated read-only cached feed at `/api/assembly-v2/feed`. The old delivery URL, HMAC secret, queue and Apps Script are unchanged. Source reads cannot create production work, run maintenance or send notifications. The new app's `RITM_ASSEMBLY_V2_FEED_URL` is pinned to the verified RITM Site and endpoint; `RITM_ASSEMBLY_V2_FEED_SECRET` stays in server runtime secrets. No credentials go to the browser. The current Site remains owner-private; collector names still represent attribution rather than access roles.

The collector loads its current local/D1 snapshot immediately and independently starts source synchronization. A shared target lease and 30-second due check coalesce concurrent viewers. Polling runs while the page is visible; the connection screen also offers an explicit refresh. Closed-browser delivery is not claimed. The source's five-minute cache/freshness boundary is visible through its confirmation timestamp; failed/partial reads retain previous target records.

`originShipmentId` preserves the exact parent RITM shipment. Each marketplace/store has its own local supply scope; complete canonical source position IDs are unchanged, including `box:sheetId`, UID/row and manual IDs. Existing UUIDs, barcode attribution, department, cut operation and historical carton norms remain pinned. New article details and capacity come from the separate imported catalog. A missing/conflicting store is an explicit “Не подтверждён” group with no boxing norm; production quantities may still be recorded. A later store change never silently moves historical work into a different scope. Direction is the original RITM name, preserved as a compatibility key; no exact marketplace warehouse ID is invented.

Imports are atomic per original RITM composition across store groups and versioned by confirmed source revision plus content hash. Stable heartbeats do not create work, new positions or workspace revisions. Source plan reductions preserve overproduction, allocations and exports. A removed source row or a supply missing from a complete fresh roster becomes inactive with its UUID/history retained; stale/partial input cannot cause retirement. DB commit guards reject work/allocation on inactive sources. The current 500-position bound applies to each store group including retained history; larger compositions are held with an explicit reason, never truncated or imported partially.

Main files: `shared/ritm.ts`, `server/ritm-api.ts`, `server/ritm-import.ts`, `server/database.ts`, `server/snapshot.ts`, `server/worker.ts`, `src/useWorkspace.ts`, `src/Setup.tsx`, `src/Collector.tsx`, `src/legacy-adapter.css`, and additive migrations `0006`/`0007`. Existing data/history tables are not dropped or rebuilt. Local preview may configure the same two keys through an untracked environment; production values use native Sites configuration.

Local verification: 46 new-app tests pass, including seven integration tests for shared IDs, mixed stores, simultaneous clients, idempotency, plan reductions, source retirement, preserved carton facts, unknown-store recording, stale-source protection, 500-position rejection and owner/origin/URL checks. Source-side verification additionally uses 70 regression/pure tests and a real compiled Workers/D1 test with network forbidden. Actual production source reads and publication are verified separately without creating fictitious RITM supplies or old Assembly work.
