# RITM — перенос работы в локальный чат

Передай эту заметку вместе с `ritm-app.zip` в новый локальный чат Codex. Она сохраняет рабочий контекст, но не является полной копией переписки.

## Инструкция для нового локального чата

Продолжай существующий проект RITM из приложенного `ritm-app.zip` в локальном рабочем пространстве. Сначала прочитай эту заметку и изучи `README.md`, `UX-CONTRACT.md` и `verification.md` внутри проекта. Не создавай приложение заново и не подключай реальную Google-таблицу без согласованной схемы полей. Сначала запусти приложение локально и проверь меню, включая мобильную ширину до 950 px.

## Цель проекта

Собрать веб-приложение для учёта данных производства RITM: печать, сборка, производство, готовый товар на складе и поставки. На первом этапе нужно надёжно собирать, сопоставлять и проверять данные. Передавать производственные задания в цеха будем позднее.

Решения пользователя:

1. Пока важнее правильно собирать данные; направление заданий в производство добавим позже.
2. Склад учитывает готовый товар.
3. Поставку создают в процессе сборки; когда она готова, пользователь внесёт её в систему.

Общаться с пользователем по-русски, коротко и понятно. Пользователь предпочитает продолжение работы без повторного согласования уже принятых решений.

## Текущее состояние

- Готов первый интерактивный прототип на React, TypeScript и Vite.
- Разделы: обзор, сборка, печать, производство, склад, поставки и источники данных.
- Есть демонстрационные данные; их нельзя выдавать за реальные производственные показатели.
- Импорт CSV реализован. Импорт заменяет снимок конкретного источника и проверяет структуру данных.
- Автоматическое чтение Google Sheets, серверная база данных, авторизация и синхронизация между пользователями ещё не подключены.
- В интерфейсе есть ссылки на источники таблиц, но их данные пока не читаются автоматически.
- Последнее исправление: на узком экране навигация открывается заметной кнопкой «Меню»; добавлены `aria-expanded` и `aria-controls`.
- Также исправлен экспорт автономной HTML-версии: она должна брать имена JS и CSS из `dist/client/index.html`, а не выбирать первый попавшийся старый файл из каталога сборки.

## Правила расчётов и данных

- KPI сборщика за день = сумма выполненных количеств, делённая на нормы операций. Нормы фиксируются для конкретных операций.
- Месячное среднее рассчитывается только по известным сменам. Выходной, отсутствие и пропуск данных не считаются нулём.
- Не суммировать одновременно итоговые FBO-количества и детальные операции-источники: это удвоит результат.
- Для печатников Дмитрия и Андрея считать фактические м² по завершённым уникальным рулонам с датой и участком (Красное здание / Ангар). Не добавлять почасовые цели без исходных данных.
- В поставке хранить маркетплейс, магазин/склад, даты готовности и прибытия, артикулы и количества. Этапы печати, резки, упаковки и отгрузки показывать отдельно, без усреднения процентов.
- Резерв товара учитывается один раз для всех поставок; резерв сам по себе не означает, что товар упакован.
- Для объединения строк использовать ID поставки, а не только артикул.

## Проверки и известные ограничения

При последней сборке прошли `npm run typecheck`, `npm run test:domain` (8 тестов), `npm run build`, SSR-проверка семи вкладок и проверка форматирования. Визуальная проверка в браузере и проверка реального нажатия меню не были выполнены: в облачной сессии браузер недоступен. Проверь это уже в локальном окружении.

В проекте доступны команды:

```sh
npm install
npm run dev -- --host 127.0.0.1
npm run typecheck
npm run test:domain
npm run build
```
